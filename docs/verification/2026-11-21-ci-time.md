# CI time — 2026-11-21

## Scope

The wall time of the `build-and-test` workflow (`.github/workflows/ci.yml`) and of
local test runs, at `3f6fff8a`, without dropping a test, lint or coverage. Follow-up to
the [test speed pass](2026-11-21-test-speed-pass.md), which made the tests themselves
faster; test execution is about 3 minutes of a Windows `check` job, compilation most
of the rest.

## Summary

`check` and `release` no longer wait about 11 minutes for the plugin jobs: they build
at once and wait only before the steps that install the plugin packages. Formatting,
Clippy and the script tests run in a job of their own, the workspace builds use every
CPU of the runner instead of two Cargo jobs, and the root workspace jobs cache their
compiled dependencies. The whole run took 23:20 with an empty cache and 19:08 with a
warm one in the experiment runs, and 28:32 and 19:31 in the first two main runs (the
first with an empty cache), against a median of 41:48 over 12 runs before (56:11 for
the last run of the old layout). Which of two kinds of Windows runner a job gets
changes its time by a quarter to a half. Locally, Cargo, libtest and the test scripts
now use every logical CPU by default (`--jobs N` limits them). The GitHub actions run on
Node.js 24, and a checking extractor of this repository unpacks the downloaded
artifacts, so no job log has a deprecation warning any more. Measured and not adopted:
rust-lld on the hosted runners (no measurable difference) and running the libraries'
doc tests at the same time (slower); measured and not changed: the engine's duplicated
unit tests and running test executables side by side. No test, lint or coverage was
dropped.

## Method

- **CI timings** come from the jobs API of each run (job created, started and completed
  times, and each step's start and end), compared with the baseline medians above.
- **Experiment runs** ran the candidate workflow on a throwaway branch: `ci-time-exp`
  added a resource sampler to `scripts-and-lint`, `check` and `release` (physical
  memory available, commit charge on Windows or swap on Linux, and free disk every 5 s,
  with the least and peak values printed at the end of the job, plus the kernel's
  out-of-memory messages on Linux) and let the branch save build caches;
  `ci-time-attribution` ran the Test step alone, without a build cache, with 2 or 4
  Cargo jobs and link.exe or rust-lld, and then built the tests with both linkers on
  one machine. Neither branch was merged, and both were deleted. Their caches (3.1 GB
  of build caches, scoped to those branches and readable by no other) could not be
  deleted with the available token; unused, they expire after seven days, and as the
  least recently used entries they go first if the repository reaches its 10 GB.
- **Local measurements** (Windows, 20 logical CPUs, 31.6 GB) built the workspace tests
  as CI's `check` job does (`CARGO_PROFILE_DEV_DEBUG=0`, `CARGO_PROFILE_TEST_DEBUG=0`,
  `CARGO_INCREMENTAL=0`, `cargo test --workspace --no-run`) in separate target
  directories with link.exe and with rust-lld, four Cargo jobs and one machine-wide
  build slot, and then ran CI's gates (`scripts/ci-workspace-tests.py
  --keep-test-artifacts --no-fail-fast`) with a private `HOST_TEST_INSTALL_ROOT`. Other
  agents built on the machine at the same time, so local wall times are indicative;
  the CI runs decide.

## Findings

### Which tests need the plugin packages

Every read of `MIDNIGHT_VIEWER_TEST_INSTALL`, `MIDNIGHT_NATIVE_TEST_INSTALLATION`,
`MIDNIGHT_IMAGE_VIEWER_TEST_APPLICATION`, `MIDNIGHT_PDF_VIEWER_TEST_APPLICATION`,
`MIDNIGHT_NETWORK_TEST_INSTALLATION`, `HOST_TEST_PLUGIN`, `HOST_BAD_PLUGIN`,
`ARCHIVE_WORKER`, `ARCHIVE_TEST_INSTALL_ROOT`, `ARCHIVE_CAPTURE_INSTALLATION` and
`MIDNIGHT_ARCHIVE_FIXTURES` in `crates/` is in an `#[ignore]`d test or in a helper that
only ignored tests call (`native_provider` in the image viewer host's startup tests, the
installed-Source test of `worker_position_tests.rs`). No script test reads
`_build/viewer-packages`, `_build/filesystem-packages` or `_build/archive-fixtures`;
only `scripts/validate.*`, `scripts/acceptance.ps1` and their tests (with fixtures of
their own) name them. The non-ignored tests use only `HOST_TEST_INSTALL_ROOT`, as a
protected root for their own fixtures (plugin host, image viewer and thumbnail host
catalogs, the engine's filesystem plugins, filesystem host discovery). So the gates can
run before the packages exist; the qualification steps after them and the release
smoke test need the packages.

### Four Cargo jobs

`CARGO_BUILD_JOBS=2` came in `5aee4d2a` (11 November) together with dev/test debug
information and incremental output off, after the Linux job had run out of disk while
linking the UI integration tests with `debuginfo=2`
([CI repair](2026-11-07-ci-repair.md)); its comment names the disk. The job count does
not change the size of the outputs, and the runners now have far more free disk than
the build uses (above). Memory decides: the generated UI bindings alone peak at about
7 GB when compiled with four threads
([Slint compile time](2026-11-18-slint-compile-time.md)), and the hosted runners have
16 GB. With four jobs, the least available memory sampled in any job was 5.4 GB on
Windows (the peak commit charge 12.1 GB of an 18.9 GB limit) and 7.2 GB on Linux,
where no swap was used and the kernel logged no out-of-memory kill; the least free disk
was 143 GB on Windows and 81 GB on Linux.

The attribution run (44919643115, same commit, no build cache, the Test step alone)
measured the job count directly:

| Test step | 2 jobs | 4 jobs |
| --- | ---: | ---: |
| Windows, link.exe (both on the faster runner kind, below) | 16:33 | 13:50 |
| Linux | 12:07 | 9:51 |

The library gate went from 714 to 576 s on Windows and from 529 to 412 s on Linux; the
gate of the ten `integration` executables hardly changed (166 → 156 s, 142 → 133 s),
since one large test crate (`midnight-ui`'s) dominates it.

### Two kinds of Windows runner

`windows-latest` jobs run on two kinds of machine, told apart by the size of their
`D:` volume. Of the 12 baseline runs, the 8 Windows `check` jobs on a 236 GB `D:`
took 15.3–19.6 minutes for the Test step and 5.1–6.8 for Clippy, the 4 on a 161 GB
`D:` 22.2–24.7 and 7.3–8.4: the second kind is about a quarter slower. In the paired
linker run below the first kind was an AMD EPYC 9V74 and the second an AMD EPYC 7763,
both with four logical processors. The kind a job gets is chance, and it moves the
Windows jobs more than most of the changes here; comparisons below therefore pair jobs
on the same kind of machine, or say which kind each ran on.

### rust-lld

Locally (method above), the rust-lld build took 892 s and the link.exe build 1,116 s,
with the same test results (7,995 passed, 161 ignored, none failed) and outputs of the
same size (702 MB of executables, PDBs 767 against 730 MB). The two builds were not
paired: library units, which do not link, were 16% faster in the rust-lld build too,
the test-executable units 34% faster, so the linker saved roughly a fifth of the test
executables' unit time on this machine.

On the hosted runners it saved nothing measurable. In the attribution run the rust-lld
leg took 22:23 for the Test step against 13:50 for link.exe, but it ran on the slower
runner kind and link.exe on the faster one. A paired run (44921978779) then built the
workspace tests twice on each of two machines, cold, four jobs, once per linker:

| Machine | First build | Second build |
| --- | ---: | ---: |
| AMD EPYC 9V74, 236 GB `D:` | rust-lld 835.7 s | link.exe 827.3 s |
| AMD EPYC 7763, 161 GB `D:` | link.exe 1,221.4 s | rust-lld 1,159.3 s |

The second build of a machine starts with warm file caches; with the order taken into
account the linkers differ by less than that order effect (±5%), while the machine kind
changes the build time by about 45%. CI therefore keeps the default linker, and
`test-execution.md` mentions rust-lld as a local option for test builds. The Windows
`check` and `scripts-and-lint` jobs of the two experiment runs below still used
rust-lld; by this measurement their times stand for link.exe as well.

### Dependency build cache

[Swatinem/rust-cache](https://github.com/Swatinem/rust-cache) 2.9.3 caches `~/.cargo`'s
registry and Git downloads and the `_build` output of every non-workspace crate; before
saving it deletes the workspace crates' artifacts, whose freshness Cargo judges by file
times that a new checkout always changes. Its key combines the job, the installed rustc
versions and hosts, the hash of the Cargo manifests, lockfiles, toolchain file and
Cargo configuration, and the `CARGO_*`, `RUST*` and compiler environment; a lockfile
change restores the newest entry of the same job, toolchains and environment and saves
a new one. It is LGPL-3.0, run unmodified in CI only (see the
[dependency policy](../dependency-policy.md#current-decisions)). sccache, the
Apache-2.0 alternative, does not cache test harnesses, binaries or proc-macros, a large
part of this build (the test executables were 1,286 s of the 3,450 s of unit time in
the local link.exe build), and its GitHub cache backend stores one entry per compiled
crate.

The first run (44919051311) saved six entries, 3.05 GB together: `check` 529 MB
(Windows) and 560 MB (Linux), `release` 577 and 626 MB, `scripts-and-lint` 373 and
383 MB. Saving took 7–38 s; restoring, with the toolchain installation in the same
step, 15–35 s. The second run (44921215320, same branch) hit all six keys. Same kind of
machine, cold → warm:

| Step | Windows | Linux |
| --- | ---: | ---: |
| Clippy | 6:34 → 3:31 (slower kind) | 3:22 → 1:57 |
| Test | 20:17 → 16:17 (slower kind) | 9:53 → 7:34 |
| Optimized release build | 19:40 → 14:09 (faster kind) | 14:46 → 11:17 |

The library gate fell from 409 to 277 s on Linux; the integration gate stayed at
132 s. Only pushes to `main` save (`save-if`), so pull requests and other branches
cannot evict main's entries; 6 entries of about 3 GB fit the repository's 10 GB cache
limit beside the plugin jobs' download caches (1.9 GB before this change). A key also
changes when a GitHub runner image updates its preinstalled stable Rust, because
rust-cache hashes every installed toolchain; the next main run then starts cold once.

### Library unit tests in the engine's integration executable

On Windows 193 of the 485 tests in `midnight-engine`'s `integration` executable are the
library's own unit tests again, compiled in through the `#[path]` includes of library
sources ([test execution](../developer/test-execution.md#targeted-test-execution)):
86 checksum, retirement and verified-output tests in each of `checksums_backend` and
`checksum_manifest_verification` (84 on Linux), and the 3 line-splitter tests in each
of the 7 Find modules (6 on Linux) that include `find_worker.rs` or `find_content.rs`. Run
alone, these 193 took 1.3–2.5 s (three rounds, local, 20 threads; the whole executable
8.4–10.6 s). Removing them needs either a `cfg` that tells the library's test build
from an include, which Cargo does not offer per target, test modules declared inside a
macro, which `cargo fmt` would no longer format, or moving those integration tests
into the library, where they would share the library's statics instead of a separate
copy each. Not changed: the duplicates cost a few seconds of a run.

### Doc tests

The doc-test gate runs rustdoc over 25 libraries and finds no doc test in any of them
(no library source has a code block in a doc comment); it took 72 s on Windows and
37 s on Linux in the baseline run. Setting `doctest = false` would save that, but it
would need a guard against a doc test added later, as the `test = false` targets have,
and it is a change to every crate's manifest. Not done; running the libraries' doc
tests at the same time was tried instead and made them slower (below).

### Every CPU by default

`.cargo/config.toml` and `api/.cargo/config.toml` set `jobs = 4` for every Cargo command,
a quarter of the development machine's 20 logical CPUs, and the native dav1d builds of
the raster plugins used 2 jobs unless `CARGO_BUILD_JOBS` was set. At first this record
kept the setting, because several agents build on that machine at once (31.6 GB, a
commit limit of 56.8 GB, which reached 54 GB during this work). The user then asked for
every core by default, configurable on the command line. Now no Cargo configuration
sets a job count, the dav1d builds default to the logical CPU count, and
`scripts/validate.*` and `scripts/ci-workspace-tests.py` take `--jobs N`, which sets
`CARGO_BUILD_JOBS` and `RUST_TEST_THREADS` to N; without it Cargo, libtest and the
scripts use every logical CPU. CI's `check` and `scripts-and-lint` jobs no longer set
`CARGO_BUILD_JOBS` either; on the four-CPU runners Cargo's default is the same four.
Where builds share a machine, `-j N` or `--jobs N` limits them.

### Running tests in parallel

libtest already runs each test executable's tests on every logical CPU, and Cargo runs
the executables of one command one after another. Summed over the 92 test executables
of the baseline run, the tests ran 114 s on Linux and 144 s on Windows (libtest's
"finished in"); `midnight-ui`'s integration executable alone took 52 and 68 s, with 966
tests keeping all four CPUs busy, and the libraries' executables with many tests did so
too. Running executables side by side would save only their tails, about 20–30 s per
job, while sharing the CPUs among tests that wait on real timing (see the
[test speed pass](2026-11-21-test-speed-pass.md)); and running them without Cargo
would need Cargo's run environment rebuilt. Locally, in the rust-lld run above, the
executables ran 82 s of the gates' 371 s; the rest was Cargo's checks before each gate,
Microsoft Defender's scan of each newly linked executable at its first start, and the
doc tests. Not changed.

The doc-test gate is the one stretch that runs strictly in series: one Cargo command
starts one rustdoc process per library after another. A candidate planned one doc-test
gate per library (`--doc` with every other library excluded) and ran the 25 gates at the
same time, at most one per CPU; in a local probe, two `cargo test` commands of one
target directory with nothing to compile had run their 6-second tests side by side in
6.5 s. In CI it was slower. In branch run 44952619697 the 25 gates took 209 s on Linux
and 99 s on Windows, against 28–37 s and 39–72 s for the single gate in the main runs
above. With one library selected, Cargo resolved other features for the shared
crates, so the gates recompiled `midnight-engine`, `midnight-ui`,
`midnight-ui-bindings` and `midnight-viewer-engine` and waited for each other on the
target directory's build lock ("Blocking waiting for file lock on build directory").
The examples gate after them then recompiled the UI crates for the workspace's features
again: 31 s on Linux and 46 s on Windows, against 5–8 s and 12–24 s. Reverted: the doc
tests stay one gate.

## Changes

- `check` and `release` no longer need the plugin jobs and start with the run. Their
  builds, and for `check` the gates, the Trash qualification and the bad-descriptor
  fixture, run first. The new `plugin-packages` action then waits for this run's
  packages (`scripts/ci-wait-for-artifacts.py`), downloads them and installs them into
  the protected root, which the `private-test-installation` action now creates without
  packages. The wait lists the nine artifacts of the runner's OS that the pattern
  downloads select (the five viewers, three filesystems and the archive fixtures; the
  release job waits for eight), fails at once when a producer leg of the same runner
  label finished without success or was skipped, retries rate limits and server
  errors, fails at once without permission, and gives up after 60 minutes. Its tests
  are `scripts/tests/test_ci_wait_for_artifacts.py`.
- The new `scripts-and-lint` job (both OSes) runs the steps that need no workspace
  build: Format, the build-script and packaging tests, the image decoder's native
  helper tests, the PowerShell tests, the source size check and the workspace Clippy
  step, unchanged. `scripts/validate.*` label those steps and `test-install` with it.
- `check` and `scripts-and-lint` build with four Cargo jobs instead of 2: at first with
  `CARGO_BUILD_JOBS=4`, now with Cargo's default (see [Every CPU by default](#every-cpu-by-default)).
- The `rust-setup` action has a `build-cache` input; `check`, `scripts-and-lint` and
  `release` cache their compiled dependencies with Swatinem/rust-cache, saved on main
  only. The plugin jobs keep the download cache.
- The workflow's permissions stay `contents: read`; `check` and `release` add
  `actions: read` for the wait.
- `scripts/tests/test_ci_workflow.py` pins that the three jobs have no `needs` and
  download nothing themselves; that no step before the wait uses a package, an
  installation variable or `--ignored`; that the waited artifacts equal the producer
  jobs' matrices and the producer list equals the jobs that upload them; the
  permissions; that `check` and `scripts-and-lint` build alike, with no job count set
  and no linker override; the cache inputs; and the Clippy step in its new job.

## Not changed

- **Waiting main runs.** The workflow's concurrency group lets one main run run at a
  time and never cancels it, but GitHub keeps only the newest waiting run of a group:
  14 of the last 40 main runs before this change were cancelled while waiting, so
  those commits got no run of their own, and a push waited up to a whole run (42
  minutes in the median) before its run started. The workflow comment that claimed
  every main commit keeps its own run now describes this. Shorter runs make both
  rarer; a group per main commit would give every commit a run at the cost of
  parallel runs competing for the account's 20 concurrent jobs (each run has 28).
- The engine's duplicated unit tests and running test executables side by side
  (above).

## GitHub action versions

Later the same day the four GitHub actions moved from v4, which targets Node.js 20, to
the current releases, which run on Node.js 24: `actions/checkout` v7.0.1,
`actions/cache` v6.1.0, `actions/upload-artifact` v7.0.2 and
`actions/download-artifact` v8.0.2 (all MIT). Their breaking changes do not touch this
workflow: download-artifact v5 changed where a single artifact downloaded by ID lands
(this workflow downloads by name, or by pattern with `merge-multiple`), v8 fails on a
digest mismatch and no longer unzips non-zip artifacts (these are uploaded zipped),
checkout v6 keeps persisted credentials in a separate file and v7 refuses fork
checkouts for `pull_request_target` and `workflow_run`, which are not used; every input
used here is unchanged. A run of the bump on a throwaway branch (44937583011) passed
every job. Scanned for "Node.js 20", "DeprecationWarning", `[DEPnnnn]` and "is
deprecated", the 28 job logs of main run 44935239554 had 184 such lines (the Node 20
notice in every job; DEP0040 and DEP0169 from cache, upload-artifact and
download-artifact; DEP0005 from download-artifact), those of 44937583011 had 26: one
DEP0005 (`Buffer()` is deprecated) per artifact download step. download-artifact v8.0.2,
its newest release, still prints it while unpacking
([actions/download-artifact#484](https://github.com/actions/download-artifact/issues/484),
open).

The user then asked for that warning to go, so download-artifact no longer unpacks.
Every download goes through the local action `.github/actions/download-artifacts`:
download-artifact v8 with `skip-decompress: true` saves each artifact's zip archive
unopened, still checking it against the SHA-256 digest recorded at upload and failing on
a mismatch, and `extract.py` (Python's `zipfile`) unpacks the archives into the
destination. The extractor refuses:

- a destination that already holds a file;
- links among the downloads and files that are not zip archives;
- members whose names are absolute or contain `..`, `:`, a backslash or a NUL;
- link and encrypted members, and two members at one path.

It fails on a CRC error. Its tests are `scripts/tests/test_ci_extract_artifacts.py`.
Without `merge-multiple`, a pattern download saves each artifact in a directory of
its own, and the extractor merges them. The first branch run failed when the Linux
`check` job extracted the viewer packages into `_build/viewer-packages`. The restored
build cache leaves empty directories below `_build`, so the destination check now
refuses files only. The next two branch runs
(44950733176 and 44952619697) passed every job, and the scan found no such line in
any of their 28 job logs.
