# Why the Slint-generated Rust is large

Historical measurement: this report records the shared-button checkpoint before
later panel modes and operation controls. Current product guidance and evidence
precedence are in the [documentation map](../README.md); later generated-source
sizes are recorded in [operations verification](midnight-explorer-operations.md).
The measurements below are not the current output size or a build-time benchmark.

The recorded shared-button pass generates **4,871,700 normalized token bytes**, or
**8,704,058 formatted bytes**. Relative to the initial frozen adapted output,
this is a 40.56% reduction in token text. It is not a claimed optimum.

The first reuse checkpoint contained 125,335 bytes of handwritten Slint in twelve
files, with `main.slint` at 70,156 bytes. Its compiler output contains 5,958,250
normalized token bytes, or 10,587,998 formatted bytes. The output expansion is
therefore substantial; it warrants checking component boundaries and build cost.
Generated source is ignored and is not the amount of code maintained by hand.

| Inventory | First reuse checkpoint A | Latest checkpoint B |
| --- | ---: | ---: |
| Normalized generated bytes | 5,958,250 | 4,871,700 |
| Formatted generated bytes | 10,587,998 | 8,704,058 |
| Component/item-tree implementations | 130 | 92 |
| Inherent methods | 2,879 | 2,142 |
| Formatted initialization code | 6,278,988 | 5,284,189 |
| Tooltip popup formatted methods | 1,404,965 | 898,938 |

In checkpoint B, initialization remains 60.7% of the formatted source, and
tooltip popup methods account for 10.3%. All Slint function methods together,
including generated helpers, total 292,369 formatted bytes. The largest remaining
costs concern component/binding/layout representation rather than a large pool
of application functions waiting to be extracted.

## Measured sources of expansion

At checkpoint A, an inventory of the actual generated file finds:

| Generated work | Formatted bytes |
| --- | ---: |
| Widget/binding initialization (`init` and `init_chunk_*`) | 6,278,988 |
| Item geometry | 837,042 |
| Layout information | 332,687 |
| Item tree | 315,776 |
| Item arrays | 297,143 |
| All Slint function methods, including generated helpers | 350,678 |

Initialization accounts for about 59.3% of the formatted output. There are about
130 generated component/item-tree types, 2,879 inherent methods, 2,079 erased
binding setups, 207 animated binding setups, 68 model binding setups and 26,428
field-offset references. Most of this implements live properties, callbacks,
layout, component ownership and item-tree/accessibility plumbing. Constants and
statics account for approximately 58KB in the separate AST inventory.

The public MainWindow API wrapper is about 89KB. Removing accessors or moving
every remaining Slint function to Rust cannot explain a reduction of several
megabytes. The generator already shares retained components, emits reusable
methods, erases binding setup and splits initialization into chunks.

There is one shared FilePane implementation and one shared TipBody implementation.
The 27 stock tooltip popup implementations still contribute about 1.40MB of
formatted methods: each has a typed parent scope, popup factory, geometry,
layout/item-tree machinery and a stock tooltip wrapper. The wrapper also retains
its default empty styled text/layout alongside our custom body. Adding another
wrapper around TipBody would not merge those parent-specific popup types.

These categories are generated source, not machine-code size, memory usage or a
runtime performance benchmark. Application/style groups mix binding and framework
plumbing with application expressions because caller inlining crosses that boundary.

## Controlled architectural comparisons

These checkpoint-A cases use the same pinned compiler/adapter and retain a real tooltip.
They are stripped diagnostic inputs, not feature-equivalent file managers.

| Diagnostic UI | Normalized generated bytes |
| --- | ---: |
| Window, text and tooltip | 101,585 |
| Two simple dynamic text-list/Flickable panes | 148,186 |
| One full current FilePane | 3,346,319 |
| Two full FilePane instances | 3,420,064 |
| Common base plus one Fluent button | 210,716 |
| Common base plus ten static Fluent buttons | 310,755 |
| Common base plus ten model-repeated Fluent buttons | 225,296 |
| Common base plus one lightweight custom button | 131,339 |

The second full pane adds only 73,745 bytes. The full pane includes navigation,
tabs, bookmarks, dropdowns, list input/rendering and their supporting controls;
the simple two-pane fixture omits most of that behavior. Its 148KB result is not
a promise that the complete application fits in that size.

The lightweight button adds approximately 30KB over the common base, compared
with 109KB for Fluent. It retains basic focus, keyboard/pointer activation and
accessibility, while omitting native styling/animations, icon handling and
checkable/primary behavior. It demonstrates a possible scale for simpler controls;
it is not a production replacement or a measured whole-application saving.

## Further changes and their limits

The adopted HintedActionButton wrapper addresses eleven remaining tooltip
children that forced native-button inlining. In a same-input-path comparison,
adapted output decreases from 5,959,150 to 4,872,600 normalized bytes: 1,086,550
bytes (18.23%). The copied diagnostic paths contribute 900 bytes relative to the
production checkpoint. The actual production output is 4,871,700 normalized bytes.
All eleven original hint expressions and callback bodies are preserved; untipped
buttons keep their original implementation. Fresh runtime verification is tracked
in the implementation plan.

Additional measurements should focus on:

1. Shared, child-free dialog bodies with explicit title/paragraph/action models,
   keeping native popup owners and distinct geometry. Help and Message currently
   occupy roughly 603KB of mixed formatted code at checkpoint B; that is not an
   expected saving.
2. Fewer distinct control/conditional variants and model-driven repeated controls,
   while preserving stable identities during pointer gestures and icon delivery.
3. A smaller shared control family, if its appearance, focus, IME, clipboard,
   accessibility, icons, menus and scrolling can be qualified against existing
   behavior. Recreating those details has a maintenance cost.
4. Upstream compiler support for more shared popup/layout representation. Parent
   references and factories need an explicit context/data interface; merging their
   generated text is unsafe. TipBody already shares its implementation; the
   remaining stock wrappers and parent scopes need a different solution.

There is no verified switch that preserves this application and reduces it by
an order of magnitude. `native` resolves to Fluent on the configured Windows and
Linux/Winit setup. Inline-all and compiler debug hooks are already off. Disabling
accessibility loses functionality; splitting generated files or shortening names
does not remove logic. An interpreter changes startup/evaluation and the binding
API and needs separate performance/security evaluation; Slint SC excludes needed
widgets and TextInput. These are architectural changes, not local reuse fixes.

Keep the AOT path while measuring smaller reusable controls. Do not promise a
percentage or a sub-megabyte complete UI before a feature-equivalent prototype
and runtime checks establish it. Add new features through shared components and
data models so the current expansion patterns do not repeat.

Local reproducible evidence remains in ignored
`.tools/slint-generated-lowerbounds/` and `.tools/slint-generated-action-hint/`.
The pinned primary sources inspected are the Rust generator, required inlining
pass, LLR expression optimizer, tooltip lowering and common tooltip style in
`i-slint-compiler` 1.18.1. No dependency registry, generated Rust text or product
features were modified to obtain the architectural comparisons.
