# CI repair

The configured remote is `TomasJelinek/fm` on GitHub. Its `build-and-test`
GitHub Actions workflow is the pipeline investigated for the reported failures.

## Observed failures and corrections

- Cargo packaging needs repository ignore files. Partial, sparse SDK checkouts
  omitted blobs that Cargo's libgit2 could not fetch lazily. SDK packaging jobs
  now use a full checkout. Independent plugin jobs still see only their own
  sources and the released public SDK bundle.
- The archive Clippy invocation lost registry configuration when `--config`
  preceded the Cargo subcommand. Passing it to `cargo clippy` fixes resolution
  for the independent Windows and Linux archive jobs.
- The Windows build-hook fixture lacked the new private-deployment script.
  It now verifies app, viewer and deployment ordering and propagates deployment
  failure, alongside application/viewer failure cases.
- `checksums_backend` path-includes the checksum controller module. Its native
  integration tests and the unit test filling all 32 job slots therefore shared
  the same process quota. Serializing only the two worker tests did not isolate
  native consumers: both local full-workspace and CI runs reproduced the failure.
  One test-only fixture now covers every real-quota consumer for the complete
  lifetime of controllers, retained results and individual result rows.
  Production admission, the 32-job limit and 64 MiB budget are unchanged.
- The shutdown test previously sampled an instantly idle shared I/O gate while
  other tests could acquire it. It now proves every permit can be reacquired
  within a bounded deadline after the blocked read exits.
- Three native-platform tests still required empty initial metadata, contrary
  to the existing optional-cache directory-service contract and Windows cached
  enumeration optimization. Shared tests now validate optional values and a
  fresh metadata query after a file changes. A separate Windows test requires
  complete cached metadata to match the native query; production listing is
  unchanged.
- A thumbnail unit fixture required an explicitly exported build directory even
  though Cargo already used the repository's `_build` configuration. It now
  retains both explicit overrides and defaults to the repository's `_build`
  fixture directory, so ordinary workspace tests do not require an extra variable.
- A physical-digit remapping fixture assigned `Ctrl+Digit1` without first
  removing the image viewer's newer default assignment. It now explicitly
  disables that binding before reassigning the chord. Conflict validation and
  actual default shortcuts remain unchanged.
- Run `42414710706` exposed a folder-size fairness assertion that compared final
  callbacks from two independent operation receivers. I/O permits are released
  before those callbacks run, so receiver scheduling can reverse their order.
  The fixture now observes the small folder's completed metadata read while the
  exclusive I/O permit is still held, requires unfinished large-folder work at
  that instant, and validates both final totals. It deliberately delays small
  result delivery until after the large result to cover the observed race.
  The production FIFO gate, scan quantum and storage concurrency are unchanged.

## 2026-11-11 follow-up: Find fixture and integration artifact lifetime

Read-only inspection of [run 42985915135](https://github.com/TomasJelinek/fm/actions/runs/42985915135)
confirmed two separate failures. The Windows job failed the Find encoding fixture;
the Linux job reported `No space left on device` during UI integration linking
(with `debuginfo=2`). [Run 42979546212](https://github.com/TomasJelinek/fm/actions/runs/42979546212)
had the same Windows assertion. Its Linux job log was unavailable (HTTP 404), so
that older Linux failure is not attributed to disk exhaustion without evidence.
The Windows job in [run 42997792507](https://github.com/TomasJelinek/fm/actions/runs/42997792507)
also failed the same Find assertion. At this inspection, its 18 independent SDK
and plugin jobs passed and its Linux application job was still running. No run
was cancelled or modified.

The fixture called `FF FE 00 00` invalid UTF-8, but the current decoder deliberately
accepts that sequence as BOM-marked UTF-16LE containing NUL. The test now retains
those bytes as a valid control and uses a UTF-8 BOM followed by an invalid UTF-8
byte for the malformed input. The original incomplete-result, error-count and
`InvalidData` checks remain. Production decoding is unchanged. The fresh Windows
application-feature gate passed all eight `find_backend` cases in 0.19 seconds;
the amended encoding case passed without weakening its error assertions.
Evidence: `_build/qa/native-operation-windows/windows-find-final.log`.

The check jobs now disable dev/test debug information and incremental output,
using two build jobs. `scripts/ci-workspace-tests.py` also runs integration target
names sequentially and retires only the successful target executables reported
by Cargo, plus their adjacent matching PDBs. A failing gate keeps its artifacts
and stops the runner. Every candidate must match the selected workspace package,
test target, profile and hashed filename inside the resolved plain repository
`_build/debug/deps` directory; symlinks, missing reports and unexpected paths
fail before deletion. There are no glob or recursive deletes and no changes to
user build directories. Retirement requires both `CI=true` and the explicit
`--retire-successful-test-artifacts` flag.

The runner preserves library tests, binary tests, doctests and default example
compilation. Only explicitly test-enabled examples execute; ordinary example
mains do not. Metadata controls disabled targets and required-feature eligibility;
duplicate integration names run together with the workspace feature graph.
Excluding a disabled library's unit/doctest target must retain its active default
features in dependent members, so gates forward the active workspace-root features
as package-qualified feature names. The pinned Cargo metadata includes inactive
platform features even with `--filter-platform`; the runner therefore uses the
native `cargo tree --depth 0 --edges normal,build,dev` roots for active features.
This helper is deliberately native-only: environment or hierarchical Cargo
`build.target` overrides and config includes are rejected before running gates,
rather than guessing cross-target output locations.

Local verification:

- The actual locked workspace plan has 23 packages, 271 gates and 266 distinct
  integration names covering 284 integration targets. Seventeen names occur in
  multiple packages. There are no mixed enabled/disabled collisions. Disabled
  `midnight-ui-bindings` unit and doctest targets are excluded; its library remains
  available as a dependency. The plan was generated with the released API 0.4
  SDK configuration without compiling the application workspace.
- Fourteen Python cases cover target selection, feature preservation, stream
  diagnostics, failed-artifact retention and cleanup boundaries. Windows passed
  13 with one symlink-privilege skip; WSL passed all 14, including that case.
- A dependency-free real Cargo workspace under the QA directory exercised a
  normal library and binary, disabled unit/doctest/integration targets, duplicate
  integration names, required features, a test-enabled example and an ordinary
  example whose main must never run. Default `cargo test --workspace --locked`
  and the runner executed exactly the same seven tests. A workspace member using
  `default-features=false` and an inactive target-specific feature exposed two
  feature-planning mistakes during development; the final fixture proves both
  active-default preservation and inactive-feature exclusion.
- All three successful integration executables and matching PDBs were retired.
  An induced failure returned 101, retained its executable/PDB and prevented a
  later target from running. The ordinary example main never ran.
