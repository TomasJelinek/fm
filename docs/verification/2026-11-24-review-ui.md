Scope: `midnight-ui`, `midnight-ui-input`, `midnight-explorer` and `midnight-compare-ui`
at `ac525b6f`. Priorities: work on the UI thread that grows with a panel's size,
event and command handling between the UI thread and the engine, `RefCell`
re-entrancy, timers, unbounded growth and `unsafe`.

The non-test sources of these crates are about 91,000 lines; the tests add about
97,000 more. This review did not read all of them line by line. The coverage below
says what was read fully, what was read in part and what was only searched.

## Findings and fixes

### Fixed

1. **Medium: the checksum window kept files waiting after a listed file never got a row**
   (`presenter/checksums.rs`, `Planned`).
   - **Cause:** the window matched a row only within the 64 listed files after the
     oldest waiting one. A file deleted between the listing and the reading pass, or
     the files of a folder that is unreadable or gone by then, pinned that window.
   - **Effect:** from the 64th later file on, no row matched. Every later file was then
     shown twice (as its row and as waiting), and the pending count stayed wrong until
     the run ended.
   - **Cost:** finding the k-th waiting row (done for every visible pending row) and
     placing the cursor became scans of up to the whole listing.
   - **Fix:**
     - Waiting files are found near the reading position (one past the furthest file
       with a row).
     - When a row is not found there, it is looked up by a hash of its name. The hash
       map is built once per run, on the first miss.
     - A listed file more than 64 files behind the reading position stops waiting and
       leaves the selection, as it does when the run ends.
     - Finding the k-th waiting file, or a waiting file's position, now scans at most
       the 64 files before the reading position.
   - **Test:** `presenter::checksums_tests::files_that_never_get_a_row_do_not_keep_later_files_waiting`
     lists 1,000 files, then deletes one file and one folder of 200 files. Before the
     fix it failed with 937 files still waiting. After the fix it passes.

2. **Medium: the Jobs list was rebuilt on every progress report**
   (`operation_presentation.rs`).
   - **Cause:** `update_model_by` replaced the whole operations model whenever any row
     differed. A running job's row changes with each report.
   - **Effect:** the Jobs window's `ListView` rebuilt every row delegate per report.
   - **Fix:** `navigation_models::update` sets only the changed rows in place while the
     jobs and their order stay the same. It replaces the model only when they change.
   - **Test:** `refresh_churn_tests::job_progress_updates_its_row_in_place_and_keeps_the_jobs_model`
     failed before the fix (the model was replaced) and passes after it.
   - **Not integrated (open):** with the in-place update,
     `native_job_windows::native_jobs_clear_actions_preserve_active_work_and_repair_selected_details`
     failed: after the last job finished, "Clear all finished" left its row. The Jobs
     window evidently learns a job's new state only from a replaced model, so the change
     was taken out; the churn remains until the Jobs window follows row changes.

3. **Medium: the thumbnail pulse never stopped while an animated tile was selected
   in a minimized window** (`midnight-explorer/src/thumbnails.rs`).
   - **Cause:** Slint still reports a minimized window as visible (`is_visible`).
   - **Effect:** a selected or hovered video or animated image kept the 100 ms pulse
     running for as long as the window stayed minimized. Each pass rebuilt targets and
     refreshed rows.
   - **Fix:** animation keeps the pulse running only while the window is not minimized.
     A restore resizes the window, and the existing geometry wake restarts the pulse.
   - **Test:** `thumbnails::pulse_tests::an_animated_thumbnail_keeps_the_pulse_until_it_is_deselected`
     now also minimizes and restores the window. Before the fix it failed with "the
     thumbnail pulse never went quiet". After the fix it passes.

4. **Low (performance): every keep-rows re-read after a full folder-size scan hashed
   every entry** (`presenter.rs`, `note_new_folders`).
   - **Cause:** each background re-read of a watched folder iterated the whole path map
     and looked up each id.
   - **Fix:** only directory rows are visited, 64 rows per word of `directory_bits`. The
     obsolete half doc comment above the function was removed.
   - **Measurement:** `presenter::tests::watch::note_new_folders_timing_over_a_million_rows`
     (ignored, run on demand). 1,000,000 rows, one in 20 a folder, Windows debug test
     build, mean of 10 runs:

     | Implementation | Time per re-read |
     | --- | --- |
     | Old (whole path map) | 640.6 ms |
     | New | 133.1 ms |

     The old implementation was measured by a temporary copy of it in the same test
     binary; that copy was then removed. Release timings were not measured.
   - **Behaviour** stays covered by `folders_the_attempted_scan_never_covered_are_not_reported_as_unfinished`.

5. **Low (performance and correctness): confirming New file scanned the whole listing,
   allocating two strings per entry on Windows** (`presenter/operations.rs`,
   `displayed_file_exists`).
   - **Cause:** the scan compared names with `to_lowercase`. That is full Unicode lower
     casing, not how Windows folders compare names.
   - **Fix:**
     - An exact-path lookup in the listing's index comes first.
     - On Windows, a scan follows that compares UTF-16 units through the same
       upper-case mapping as the path bar (`name_case`), with no allocation.
   - **Test:** `presenter::tests::operations::a_new_empty_file_asks_only_for_a_listed_file_in_the_folder_s_letter_case_rules`
     covers the exact name, a folder name, and other letter case on Windows and Linux.
     It passes before and after the fix, and pins the behaviour of the faster lookup.

### Open (not fixed, with reasons)

Follow-up: every item below but the first (the update confirmation), and the Jobs
window's in-place rows of Medium finding 2, were fixed on 24 November
([UI performance fixes](2026-11-24-ui-perf-fixes.md)).

- **Low: the update confirmation depends on the startup settings read**
  (`midnight-explorer/src/updates.rs`, `schedule_startup`).
  - `apply::confirm` runs only after `PreferencesLoaded` was applied.
  - If the initial `LoadPreferences` send is refused (the engine queue is full at
    startup), the 500 ms timer polls for the rest of the run. The updater's
    confirmation window can then roll back an update that started fine.
  - A read slower than the confirmation window does the same.
  - This is rare. The fix changes the update contract (confirm after reveal, without
    settings), so it needs an architecture decision.
- **Low: closed comparator windows stay allocated until another comparator opens or the
  app exits** (`midnight-compare-ui/src/lib.rs`, `OpenWindow::close`). The hidden
  component stays, and so does any output left in the session mailbox. The two-window
  limit bounds this.
- **Low: the drag bridge polls every 250 ms for the whole run** (`drag_bridge.rs`,
  `IDLE_POLL`). This is documented as a deliberate safety net. Stopping it needs every
  region change to wake the bridge first.
- **Low: checksum Select all notifies every row** (`checksum_windows.rs`,
  `Rows::marks_changed`). That is one `row_changed` per row, for example 100,000 per
  Ctrl+A.
- **Low: jump to the next selected row in an archive folder looks up every selected
  member** (`presenter/selected_navigation.rs`). That is O(selected) per key press.
- **Low: Find in a command's output lower-cases every line on each search**
  (`command_output_windows.rs`, `Rows::find`). That is up to 50,000 allocations per
  search.

### Checked and found sound

- **`unsafe`:** every block borrows a live window handle on the UI thread and retains
  no pointer. Out-parameters are sized correctly, and Xlib allocations are freed on
  every path.
- **Engine-to-UI wake:** `WakeGate` uses read-modify-write on both sides. A publication
  is therefore either rechecked or schedules a new callback. The drain is bounded (16
  events or 3 ms) and reschedules only while work can progress.
- **Timers:** no timer captures a strong handle to its own window. Every repeated timer
  that should stop when idle does stop: `Pulse`, the size refresh, the compare batch
  timer and native scrolling. The documented drag-bridge safety net is the exception.
- **`RefCell`:** `refresh` runs under a shared presenter borrow. Handlers that can run
  during a refresh use `try_borrow_mut`. No borrow is held across an `await`.
- **Caches and queues are bounded:**
  - thumbnail images: LRU, 4,096 entries, 54 MiB
  - command output: 50,000 lines
  - Find results: 10,000
  - job row cache: pruned per refresh
  - thumbnail routing receipts: 128
  - directory pins: 16
- **Panel row model:** it is virtualized. Per-refresh status values (selected, hidden
  and match counts) are O(1).
