# Implementation backlog

This backlog lists the work that remains: missing or partial behaviour, decided changes
that are not implemented yet, known limits with the trigger that reopens them, and
qualifications that have not run. What is implemented is in
[feature status](FEATURE_STATUS.md); the [current checkpoint](ACTIVE_WORK.md) names the
work in flight. IDs are stable because other documents and code comments refer to them;
a row is removed when its work is done, and the Git history keeps it.

Each row gives the ID with its priority or state, the current behaviour and the gap, and
the trigger, next step and owner role (the roles of [AGENTS.md](../AGENTS.md)). Rows
apply to Windows x64 and Linux x86-64 unless they name a platform; macOS is PLAT-01.

- **States:** *partial* (implemented in part), *open* (not implemented), *validation*
  (implemented; a named qualification has not run), *documented limit* (accepted
  behaviour with a trigger that reopens it), *deferred* (waits for its trigger or a
  measurement), *decision open* (needs an Architect or product decision), *later* (a
  separate extension).
- **Priorities**, where given: P0 is an integrity prerequisite, P1 functional or
  reliability work, P2 qualification or optimization.
- **Closing a row** needs the source, the native workflow, failure, cancel and race
  evidence and the platforms tested, recorded in a dated record or an acceptance record.
  A design, an enabled button or a happy-path check alone does not close a row, and a
  test or CI job that exists is not evidence that it passed. Preserve separate OS
  implementations, backend I/O, raw Unicode identities, no `MAX_PATH`, bounded queues
  and worker cleanup. Dependency changes follow the [dependency policy](DEPENDENCY_POLICY.md)
  and update the [inventory](THIRD_PARTY.md).
